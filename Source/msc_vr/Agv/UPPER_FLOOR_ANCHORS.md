# 상층(2·3층) 내비게이션 앵커 작업 메모 (2026-10-27)

지게차가 2·3층에서 랙 사이로 이동하려면 경로 계획용 앵커가 필요하다는 점과, 그 위치·분담에 대한 **메모**다. 구현된 기능이 아니다. 아래 "확인한 사실"은 2026-10-27 저장 맵(`/Game/FirstPerson/Lvl_FirstPerson`)을 읽기만 해서 얻었고(맵 저장·재생 없음), "초안"은 검증하지 않았다. 승강기 장치·절차는 [MEZZANINE.md](../../../MEZZANINE.md), [ELEVATOR_MODEL.md](../../../ELEVATOR_MODEL.md)를 따른다. 전체 설계안은 [NAVIGATION_REDESIGN.md](NAVIGATION_REDESIGN.md), 지금까지의 이동 수정은 [MOTION_SPEED_PORT.md](MOTION_SPEED_PORT.md)다.

## 1. 확인한 사실

### 앵커 현황
- 두 차량(1호·2호)의 `NavigationAnchors`는 **각 31개, 모두 1층(z=0)** 에 있다. 2층 이상은 0개다. 두 차량의 목록은 같다.
- 일부는 중복이다(예: (1030,−1790)이 방향 0°·90°로 2번, (700,−1570)이 0°·180°로 2번). 좌표 일부는 정확히 같은 점이 두 번 들어 있다.
- 1층 앵커는 손으로 적은 좌표다. `Scripts/warehouse_staging_layout.py`의 `NAVIGATION_ANCHORS` 26개를 설정 스크립트(`configure_fleet_corridors.py`, `configure_inbound_area.py`)가 차량에 복사하고, `configure_warehouse_waiting_bays.py`가 (2050, −640/−140/300/650/1150) 5개를 더한다. 지오메트리에서 계산하는 코드는 없다.
- 배치 편집기(`WarehouseLayoutEditor.cpp`)는 앵커를 새로 만들지 않고, 충전기·승강기·랙을 옮길 때 근처의 기존 앵커를 같이 옮긴다.
- 승강기 `MZ_AGVElevator`는 (1000,1600,0)에 있고, 층별 대기 지점은 (1000,1100,Z)다. 승강기 앞 대기 지점을 앵커로 둔 곳은 없다.

### 경로 계획이 앵커를 쓰는 방식
- `PlanAutonomousRoute`는 먼저 출발점에서 목표까지 곡선·직선으로 직접 연결을 시도한다. 막힐 때만 앵커를 징검다리로 쓴다.
- 앵커 후보는 **차량과 같은 높이(z 차이 1cm 미만)** 인 것만 쓰고, 층별로 40개까지 센다(`WarehouseForkliftAI.cpp`의 `FloorCandidates`). 각 후보는 충돌 검사(`NavigationClear`)를 통과해야 노드가 된다. 잘못 놓인 앵커는 쓰이지 않을 뿐이다.
- 즉 층 안의 계획 로직은 1층과 같고, **상층 앵커 데이터만 있으면 된다.**

### 2층(z=400) 구조
| 구역 | 범위 (cm) |
| --- | --- |
| 중앙 개방부(바닥 없음) | x −500~500, y −1300~1300 |
| 왼쪽 갤러리 바닥 | x −1800~−500, 전 구간 y. 화물 승강기용 절단이 x −1140~−960, y 1360~1540 |
| 오른쪽 갤러리 바닥 | x 500~1800, y −1800~1419 |
| 북쪽 연결 바닥 | x −500~500, y 1300~1800 |
| 남쪽 연결 바닥 | x −500~500, y −1800~−1300 |
| 승강기 주변 바닥 | x 500~859 및 1141~1800, y 1424~1800 (승강기 구덩이 x 859~1141) |
| 랙 | 왼쪽 x −1600~−1500, 오른쪽 x 1500~1600, 깊이 100. 양쪽 각 4개 베이이고 y는 −1083~−817, −283~−17, 517~783, 1017~1283 |
| 계단 | 서쪽 끝 x −1945~−1695(차량 통로 밖) |

- 2층은 중앙 개방부를 둘러싼 **고리 모양**이다. 왼쪽·오른쪽 갤러리가 북쪽·남쪽 연결 바닥(폭 약 500)으로 이어진다.
- 승강기에서 내리면 오른쪽 갤러리 북단(1000,1100)이다. 왼쪽 갤러리로 가려면 북쪽 연결 바닥을 건너야 하고, 이곳이 직선 연결이 막히는 첫 위치다.
- 3층은 랙 부품 80개(x ±1600, y −1083~1283), 화물·팔레트 각 24개, 구조물 범위(±2024×±1850)가 2층과 같게 조회됐다. 계단 개구부 등 일부는 층마다 다를 수 있어 확인이 필요하다.

## 2. 앵커 템플릿 초안 (미검증)

2층 기준이며 3층은 z=800으로 복제한다. 모든 점은 충돌 검사를 통과한 것만 쓰인다.

| 구간 | 점 (x, y) | 방향 |
| --- | --- | --- |
| 오른쪽 갤러리 중심선 | (1000, 1100), (1000, 700), (1000, 300), (1000, −100), (1000, −500), (1000, −900), (1000, −1300), (1000, −1500) | 90°와 −90° 쌍 |
| 왼쪽 갤러리 중심선 | (−1000, 1100), (−1000, 700), (−1000, 300), (−1000, −100), (−1000, −500), (−1000, −900), (−1000, −1300), (−1000, −1500) | 90°와 −90° 쌍 |
| 북쪽 연결 | (700, 1350), (0, 1550), (−700, 1350) | 0°와 180° 쌍 |
| 남쪽 연결 | (700, −1450), (0, −1550), (−700, −1450) | 0°와 180° 쌍 |

- 랙 앞 최종 접근 자세는 작업 지시마다 `PalletApproach`가 계산한다. 앵커는 갤러리 중심선까지 데려다주는 역할만 한다.
- 화물 승강기 절단(x −1140~−960, y 1360~1540) 근처의 왼쪽 갤러리 점은 제외하거나 충돌 검사로 걸러진다.
- 난간과 개방부 가장자리에서 충분히 떨어진 중심선만 쓴다. 지도(건물 구조 태그)에 상층 난간·바닥이 들어 있는지는 확인하지 않았다.

## 3. 분담 제안
1. 좌표와 방향은 이동 담당이 정한다. 이 문서의 표를 시작점으로 충돌 검사와 경로 시험으로 다듬는다.
2. 맵에 넣고 저장하는 일은 맵 파일을 자주 바꾸는 쪽이 한다. 1층 방식과 같이 스크립트 한 개(차량에 `navigation_anchors` 설정)로 적용한다.
3. 적용 뒤 이동 담당이 경로 시험으로 확인한다.
4. 이후 단계에서 실행 시점 자동 생성으로 바꾸면 배치 편집에 따라 앵커가 갱신된다. 이것은 지금 있는 기능이 아니라 제안이다.

## 4. 확인할 시험
- 승강기 하차 → 오른쪽 갤러리 랙 앞 → 북쪽 연결 → 왼쪽 갤러리 랙 앞 경로가 계획·주행되는가(2층·3층 각각).
- 같은 경로의 1배속·4배속 결과가 같은가.
- 두 대가 같은 층의 좁은 연결 바닥을 건너는 경우.
- 앵커가 없는 현재 상태에서 같은 경로가 실패하는지 먼저 확인해 효과를 비교한다.

## 5. 아직 모르는 것
- 갤러리·연결 바닥의 실제 통행 가능 폭(랙, 난간 기둥, 개방부 가장자리 여유 포함)
- 상층 바닥·난간의 지도 태그 여부
- 계단 개구부와 층별 차이
- 실제 저장 맵의 상층에서 랙 사이 경로가 지금 되는지(임시 시험 공간의 층간 운반 시험은 통과했으나, 그 공간의 지오메트리는 단순하다)
